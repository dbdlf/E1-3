# Mini NPU Simulator

AI 모델이 하는 핵심 계산인 **MAC(Multiply-Accumulate) 연산**을 직접 구현해서, 입력 패턴이 **십자가(Cross)** 와 **X** 중 어느 쪽에 가까운지 판별하는 Python 콘솔 프로그램입니다.
3×3 사용자 입력과 `data.json`(5×5, 13×13, 25×25)을 분석하고, 크기별 연산 시간을 측정해 시간 복잡도 O(N²)를 확인합니다.

- Python 3.8 이상, **표준 라이브러리만 사용** (`json`, `time`, `re`, `math`, `os`, `sys`, `unicodedata`)
- NumPy 등 외부 라이브러리는 쓰지 않았고, MAC 연산은 이중 반복문으로 직접 구현했습니다.

## 2. 구현 설계

### 2-1. 전체 흐름 한눈에 보기

```
main()
 └─ choose_mode()
     ├─ 1 → run_user_mode()
     │       read_matrix() ×3 ─▶ Matrix ─▶ mac(패턴, A) · mac(패턴, B) ─▶ judge() ─▶ 결과 출력
     │                                     └─ measure_ms() : 이 연산 구간만 시간 측정
     └─ 2 → run_json_mode(path)
             load_json() ─▶ load_filters() ─▶ filters = {N: {"Cross": Matrix, "X": Matrix}}
             patterns 순회 ─▶ evaluate_case() ─▶ mac() ×2 ─▶ judge() ─▶ PASS / FAIL
             benchmark_sizes() ─▶ print_perf_table() ─▶ print_summary()
```

함수마다 맡은 일이 하나씩입니다.

| 역할 | 함수 |
|---|---|
| 입력과 파싱 | `read_matrix()`, `parse_row()`, `load_json()` |
| 검증 | `Matrix.from_rows()`, `parse_filter_entry()`, `evaluate_case()` |
| 계산 | `mac()` |
| 판단 | `is_tie()`, `judge()` |
| 출력 | `print_case()`, `print_perf_table()`, `print_summary()` |

계산 함수 `mac()`은 `input()`, `print()`, 파일 읽기를 전혀 하지 않습니다. 그래서 모드 1과 모드 2가 같은 함수를 그대로 쓸 수 있고, 시간을 잴 때도 "연산만 하는 구간"을 깔끔하게 떼어 낼 수 있습니다(2-8절).

### 2-2. 데이터 구조 — `Matrix`
- n×n 2차원 리스트를 감싼 클래스입니다. `get(row, col)` / `set(row, col, value)`로 특정 위치의 값을 읽고 씁니다. 범위를 벗어나면 `IndexError`가 납니다.
- `Matrix.from_rows(rows)`는 JSON 배열을 검증해서 행렬로 바꿉니다.
  - 배열인지, 정사각형인지(각 행의 열 수 = 행 수), 모든 값이 유한한 숫자인지 확인합니다. `bool`, 문자열, `NaN`, `inf`는 거부합니다.
- 크기에 제한이 없어서 3×3, 5×5, 13×13, 25×25는 물론 400×400도 처리합니다. (4-3절 보조 측정 참고)

### 2-3. MAC 연산 흐름 — 입력 → 위치별 곱셈 → 누적 합산 → 점수 반환

```python
def mac(pattern, filt):
    if pattern.n != filt.n:                      # ② 크기 확인
        raise ValidationError(...)
    n = pattern.n
    p_data = pattern.data
    f_data = filt.data
    total = 0.0                                  # 누산기(accumulator) 초기화
    for i in range(n):
        p_row = p_data[i]
        f_row = f_data[i]
        for j in range(n):
            total += p_row[j] * f_row[j]         # ③ 같은 위치끼리 곱하고 ④ 누적
    return total                                 # ⑤ 점수 반환
```

| 단계 | 코드 위치 | 하는 일 |
|---|---|---|
| ① 입력 | `read_matrix()` / `Matrix.from_rows()` | 콘솔 줄이나 JSON 배열을 검증해 `Matrix`로 만듭니다. 이 시점부터 모든 값은 `float`이고 정사각형임이 보장됩니다. |
| ② 크기 확인 | `mac()` 첫 줄 | 패턴과 필터의 크기가 다르면 계산하지 않고 `ValidationError`를 던집니다. |
| ③ 위치별 곱셈 | `p_row[j] * f_row[j]` | 같은 (i, j) 위치의 값끼리만 곱합니다. |
| ④ 누적 합산 | `total += ...` | 곱한 값을 누적 변수 하나에 계속 더합니다. 하드웨어 MAC 유닛의 누산기(accumulator) 레지스터가 하는 일과 같습니다. |
| ⑤ 점수 반환 | `return total` | `float` 점수 하나를 돌려줍니다. 어느 쪽이 이겼는지 비교하는 일은 `mac()` 밖의 `judge()`가 맡습니다. |

- 반복문 안에서는 `get()`을 부르지 않고 내부 리스트를 직접 읽습니다. 크기는 ①, ②에서 이미 검증했습니다. 그런데 `get()`을 쓰면 메서드 호출과 범위 검사가 N²번 반복되어 측정 시간이 "곱셈·덧셈"이 아닌 비용으로 부풀기 때문입니다.
- 행 참조(`p_row`, `f_row`)를 바깥 반복문에서 미리 꺼내 두어, 안쪽 반복문의 인덱싱을 한 단계 줄였습니다.

### 2-4. 패턴 키에서 N 추출 → `size_N` 필터 매칭

1. **필터 로드** — `FILTER_KEY_RE = ^size_(\d+)$`로 필터 키에서 N을 뽑습니다. 그리고 **정수 N을 키로 하는** 딕셔너리 `filters[N] = {"Cross": Matrix, "X": Matrix}`에 저장합니다. 이때 행렬의 실제 크기가 N×N인지도 확인합니다. 예를 들어 `size_5`인데 4×4이면 그 크기만 로드 실패로 처리하고, 사유를 `filter_errors[N]`에 남깁니다.
2. **패턴 키 해석** — `PATTERN_KEY_RE = ^size_(\d+)_(\d+)$`로 패턴 키를 읽습니다. 첫 번째 그룹이 크기 N이고, 두 번째 그룹은 같은 크기 안에서의 번호(idx)입니다.
3. **필터 선택** — `filters[N]`을 딕셔너리에서 바로 찾습니다(O(1)). 그 크기의 필터가 로드에 실패했으면 그 사유로, 아예 없으면 "size_N 필터가 없습니다"로 FAIL 처리합니다.
4. **실제 크기 재확인** — 키가 말하는 N과 별개로, `input` 배열의 실제 크기를 필터 크기와 한 번 더 비교합니다. 키는 `size_3_3`인데 4×4 배열이 들어 있으면 `크기 불일치` FAIL입니다.

설계에서 신경 쓴 점은 다음과 같습니다.
- `split('_')` 대신 **문자열 전체가 맞아야 하는 정규식**을 썼습니다. 그래서 `pattern_1`, `size_5_a` 같은 잘못된 키를 확실히 걸러 냅니다.
- 문자열 `"size_5"`가 아니라 **정수 N으로 매칭**합니다. 그러면 필터 키와 패턴 키의 표기 차이에 흔들리지 않습니다. 또 성능 표를 5 → 13 → 25 숫자 순서로 정렬할 수 있습니다. 문자열로 정렬하면 `size_13` < `size_25` < `size_5`가 됩니다.
- **키를 그대로 믿지 않습니다.** "키가 말하는 크기"와 "데이터의 실제 크기"를 따로 검증하기 때문에, 라벨링 실수가 있어도 잘못된 필터로 계산하지 않습니다.

### 2-5. 라벨 정규화 — `normalize_label()`
프로그램 내부에서는 **표준 라벨 `Cross`, `X` 두 개만** 사용합니다. 바깥 데이터의 표기는 모두 `normalize_label()` 한 곳에서 변환합니다.

| 원본 표기 (앞뒤 공백 제거, 대소문자 무시) | 표준 라벨 |
|---|---|
| expected `'+'`, filter 키 `'cross'` | `Cross` |
| expected `'x'`, filter 키 `'x'` | `X` |
| 그 밖의 값 (예: `'o'`) | 정규화 실패 → 해당 케이스 FAIL `[라벨 정규화]` |

**정규화를 하는 이유**: `data.json`은 같은 뜻을 서로 다른 기호로 씁니다. 정답(expected)은 `'+'`/`'x'`, 필터 키는 `'cross'`/`'x'`입니다. 이 문자열을 그대로 비교하면 판정 결과 `"cross"`와 정답 `"+"`는 영원히 다르다고 나와서, 로직이 맞아도 FAIL이 됩니다. 입력 지점에서 표준 라벨로 한 번 통일해 두면, 출력과 PASS/FAIL 비교가 모두 같은 기준(`Cross`/`X`)으로 이루어집니다.

**별도 함수로 분리한 이유와 장점**
- **규칙이 한 곳에만 있습니다.** 변환 규칙은 `LABEL_ALIASES` 표 하나와 `normalize_label()` 함수 하나뿐입니다. expected 값과 필터 키가 같은 함수를 거치므로, 두 경로가 서로 다른 규칙을 쓰게 될 위험이 없습니다.
- **입구에서 한 번만 변환합니다.** 데이터가 들어오는 지점(`parse_filter_entry()`, `evaluate_case()`)에서만 호출합니다. 그 뒤의 판정, 출력, 비교 코드는 표준 라벨만 압니다. 내부 로직은 `'+'`라는 표기가 있다는 사실조차 몰라도 됩니다.
- **확장이 쉽습니다.** `'plus'`, `'×'` 같은 새 표기는 `LABEL_ALIASES`에 한 줄만 추가하면 됩니다. 판정 코드는 고칠 필요가 없습니다.
- **테스트가 쉽습니다.** 입력만 받아 결과만 돌려주는 순수 함수라서 `normalize_label(' X ') == 'X'`처럼 따로 떼어 검증할 수 있습니다.
- **모르는 표기를 조용히 넘기지 않습니다.** 알 수 없는 값이면 `None`을 돌려주고, 호출하는 쪽에서 `[라벨 정규화]` FAIL로 분류합니다. 이상한 라벨이 기본값으로 둔갑해 PASS가 되는 일이 없습니다.

### 2-6. 점수 비교 정책 (epsilon)과 모드별 동점 처리
- `abs(score_a - score_b) < 1e-9` 이면 **동점**으로 봅니다(`is_tie()`).
- 동점이 아니면 점수가 큰 쪽의 라벨로 판정합니다(`judge()`).
- 진단을 돕기 위해 동점 FAIL 사유에 **"epsilon 없이 `>`로만 비교했다면 어떻게 판정됐을지"** 도 함께 출력합니다.
- 1e-9를 고른 이유는 두 가지입니다. 이번 데이터의 반올림 오차(1e-16 ~ 1e-15)보다는 충분히 크고, 의미 있는 점수 차이(데이터의 최소 단위 0.1)보다는 충분히 작습니다. 왜 오차가 생기는지는 5-3절에서 설명합니다.

동점을 **판단하는 규칙**(`is_tie()`, `EPSILON = 1e-9`)은 두 모드가 함께 씁니다. 다만 동점을 **표현하고 집계하는 방식**은 모드의 목적에 맞게 다르게 두었습니다.

| | 모드 1 (사용자 입력) | 모드 2 (data.json 분석) |
|---|---|---|
| 판정 라벨 | `A` / `B` | `Cross` / `X` |
| 동점일 때 출력 | `판정 불가 (\|A-B\| = … < 1e-9)` | `UNDECIDED` |
| 정답(expected) | 없음 | 있음 |
| 동점의 결과 | 결과로 보여 주고 끝 (PASS/FAIL 개념 없음) | **FAIL로 집계**, 사유 `[수치 비교(동점)]` |

요구사항 관점에서 이렇게 나눈 이유는 다음과 같습니다.
- **모드 1은 사람이 쓰는 대화형 계산기입니다.** 필터 A, B는 사용자가 마음대로 넣는 값이라, 프로그램은 A가 십자가인지 X인지 알 수 없습니다. 그래서 `Cross`/`X`가 아니라 입력한 이름 그대로 `A`/`B`로 답하고, 동점은 사람이 읽기 쉬운 문장인 "판정 불가"와 그 근거(|A-B|)로 보여 줍니다. 비교할 정답이 없으니 PASS/FAIL도 없습니다. 요구사항도 "판정 결과(A/B/판정 불가)"로 정해 두었습니다.
- **모드 2는 expected와 자동으로 비교하는 일괄 테스트입니다.** 결과를 기계적으로 비교하고 집계해야 하므로, 판정은 정해진 라벨 집합 `{Cross, X, UNDECIDED}` 중 하나여야 합니다. 요구사항도 "판정(Cross/X/UNDECIDED)"과 "동점은 FAIL"을 명시합니다.
- **동점을 FAIL로 집계하는 이유**: 테스트가 묻는 것은 "프로그램이 expected를 맞혔는가"입니다. 결정을 내리지 못했다면 맞힌 것이 아닙니다. "동점이면 Cross" 같은 임의의 규칙으로 PASS를 만들면, 필터가 두 모양을 구별하지 못한다는 사실이 결과에서 사라집니다.

### 2-7. 입력 검증과 오류 처리
| 상황 | 처리 |
|---|---|
| 모드 선택에 1, 2 외의 값 | 안내 후 다시 입력 |
| 모드 1: 한 줄의 숫자 개수가 3이 아님 (열 수 불일치) | `입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요.` → **그 줄만** 다시 입력 |
| 모드 1: 빈 줄 (행 수 부족) | 행 수 부족 안내 → 그 줄 다시 입력 |
| 모드 1: 숫자로 바꿀 수 없는 값, `inf`/`nan` | 숫자 파싱 오류 안내 → 그 줄 다시 입력 |
| 모드 2: 파일 없음 / JSON 문법 오류 | 오류 메시지 출력, 케이스 0개로 요약까지 정상 진행 |
| 모드 2: 필터가 정사각형이 아님, 키의 N과 크기가 다름, cross/x 누락 | 그 크기 필터만 로드 실패. 그 크기를 쓰는 패턴은 FAIL `[데이터/스키마]` |
| 모드 2: 패턴 키가 `size_{N}_{idx}` 형식이 아님 | FAIL `[데이터/스키마]` |
| 모드 2: 키의 N에 해당하는 필터 없음 | FAIL `[데이터/스키마]` |
| 모드 2: **패턴과 필터의 크기 불일치** | FAIL `[데이터/스키마]` `크기 불일치: 패턴 4×4 ≠ size_3 필터 3×3` |
| 모드 2: input/expected 누락, 숫자가 아닌 값 | FAIL `[데이터/스키마]` |
| 모드 2: 예상 못 한 예외 | 해당 케이스만 FAIL로 격리하고 다음 케이스 계속 |
| 입력 스트림 종료(EOF), Ctrl+C | 안내 문구 후 정상 종료 (traceback 없음) |

FAIL 사유는 `데이터/스키마`, `라벨 정규화`, `수치 비교(동점)`, `판정 불일치` 네 가지로 분류해 출력합니다. 그래서 실패가 나면 **데이터 문제인지, 로직 문제인지, 수치 비교 문제인지** 바로 구분할 수 있습니다.

### 2-8. 성능 측정 — "연산 구간"의 경계

```python
def measure_ms(func, repeat=REPEAT):
    func()                                     # 워밍업 1회 (측정 제외)
    total = 0.0
    for _ in range(repeat):
        start = time.perf_counter()            # ── 측정 시작
        func()                                 #    연산만 실행
        total += time.perf_counter() - start   # ── 측정 끝
    return total / repeat * 1000.0             # 평균(ms)

def benchmark_mac(pattern, filt, repeat=REPEAT):
    return measure_ms(lambda: mac(pattern, filt), repeat)   # 측정 대상은 mac() 하나
```

- **측정 전에 끝나는 일**: 콘솔 입력(`input()`), 파일 읽기(`json.load`), 검증(`Matrix.from_rows()`). 측정이 시작될 때 데이터는 이미 메모리 안의 `Matrix`로 준비되어 있습니다.
- **측정 구간**: `perf_counter()` 두 번 사이에는 `mac()` 호출만 있습니다. 그 안에서는 `print`, `input`, `open`을 하지 않습니다.
- **측정 후에 하는 일**: 결과 출력(`print_perf_table()`, `print()`).
- `time.time()` 대신 `time.perf_counter()`를 썼습니다. 시스템 시계 보정의 영향을 받지 않고 항상 앞으로만 가는 고해상도 시계이기 때문입니다.
- 첫 호출에만 생기는 일회성 비용을 빼려고 워밍업 1회를 측정에서 제외합니다. 그다음 **10회를 각각 측정해 평균**을 냅니다.
- 반복마다 따로 재기 때문에 `perf_counter()` 호출 자체의 비용(수십 ns)도 함께 잡힙니다. 3×3처럼 아주 짧은 연산에서는 이 고정 비용이 눈에 띕니다(4-3절 해석).
- 모드 1 결과의 "연산 시간"은 판정에 필요한 MAC 2회(A, B)를 합한 값입니다. 성능 표는 **MAC 1회** 기준이라서 표의 연산 횟수 N²과 정확히 대응합니다.
- 표에는 `크기(N×N) / 평균 시간(ms) / 연산 횟수(N²)`를 싣고, 복잡도 분석을 돕기 위해 `MAC 1회당(ns)` = 평균 시간 ÷ N² 도 함께 보여 줍니다.
- 모드 1은 3×3을 측정합니다. 모드 2는 3×3(미션 소개의 십자가 필터와 X 패턴)과 data.json의 5×5, 13×13, 25×25를 측정합니다.

### 4-2. 실패 원인 분석

실패 3건을 **데이터/스키마 문제 → 로직 문제 → 수치 비교 문제** 순서로 하나씩 점검했습니다.

**① 데이터/스키마·라벨 문제인가? → 아니다.**
세 필터(size_5, 13, 25)는 모두 정사각형이고, 키의 N과 크기가 같고, cross/x가 모두 있어서 정상 로드되었습니다. 6개 패턴도 키 형식(`size_{N}_{idx}`), 크기(패턴 N×N = 필터 N×N), 숫자 값 검증을 모두 통과했습니다. expected `'x'`, `'+'`도 각각 `X`, `Cross`로 정상 정규화되었습니다. 그래서 FAIL 분류에 `데이터/스키마`나 `라벨 정규화`는 0건입니다.

**② MAC 로직 문제인가? → 아니다.**
점수를 손으로 계산한 값과 비교했습니다.
- size_5_2: 십자가 입력 9칸 중 가운데 1칸은 0.9, 나머지 8칸은 1.0 → 8 × 1.0 + 0.9 = **8.9** ✔
- size_25_2: 십자가 입력 49칸 → 48 × 1.0 + 4.9 = **52.9** ✔
- size_13_1: X 입력 25칸 → 24 × 0.3 + 7.5 = **14.7** ✔

출력값과 모두 일치하고, 나머지 3건도 정상적으로 PASS입니다. 로직(곱셈, 누적, 큰 쪽 선택)에는 문제가 없습니다.

**③ 수치 비교(동점) 문제다 — 근본 원인은 필터 가중치 설계.**
실패한 세 케이스는 **수학적으로 두 점수가 정확히 같도록** 필터 가중치가 정해져 있습니다.

| 케이스 | Cross 필터 쪽 계산 | X 필터 쪽 계산 | 실수 계산 결과 |
|---|---|---|---|
| size_5_1 (X 입력) | 가운데 0.9 × 1 = 0.9 | 대각선 9칸 × 0.1 = 0.9 | 0.9 vs 0.8999999999999999 |
| size_13_2 (십자가 입력) | 십자가 25칸 × 0.3 = 7.5 | 가운데 7.5 × 1 = 7.5 | 7.499999999999997 vs 7.5 |
| size_25_1 (X 입력) | 가운데 4.9 × 1 = 4.9 | 대각선 49칸 × 0.1 = 4.9 | 4.9 vs 4.899999999999999 |

- 0.1, 0.3은 2진수 부동소수점으로 정확히 나타낼 수 없습니다. 그래서 여러 번 더하면 마지막 자리에 1e-16 ~ 1e-15 수준의 오차가 쌓입니다. 이 때문에 "같아야 할" 두 점수가 아주 조금 다르게 나옵니다.
- 이 차이(최대 2.66e-15)는 허용오차 1e-9보다 백만 배 이상 작습니다. 따라서 epsilon 정책에 따라 **동점(UNDECIDED)** 이 되고, expected와 다르므로 FAIL입니다.
- **epsilon 없이 `>`로만 비교했다면** 판정은 반올림 오차의 방향에 따라 정해졌을 것입니다. 실제로 size_5_1 → Cross, size_13_2 → X, size_25_1 → Cross로 **셋 다 정답과 반대**가 나옵니다. 즉 epsilon이 없어도 결과는 여전히 FAIL입니다. 다만 이 경우 "판정 불일치"로 보여서 **로직 버그처럼 오진하게** 됩니다. epsilon 정책 덕분에 진짜 원인(필터가 이 입력을 구별하지 못함)이 `수치 비교(동점)`로 정확히 드러납니다.

**결론 및 개선 방향**
- 3건 모두 `수치 비교(동점)` 분류이며, 근본 원인은 **data.json 필터 가중치 설계(데이터 문제)** 입니다. 프로그램 로직의 결함은 아닙니다.
- PASS 수를 늘리려고 data.json이나 expected를 고치거나 epsilon을 0으로 낮추지 **않았습니다**. 그렇게 하면 문제를 숨기는 것이고, 반올림 오차에 판정을 맡기게 되기 때문입니다.
- 필터 가중치가 어떻게 동점을 만드는지는 MAC 점수가 가중치 크기에 영향을 받는 성질과 관련이 있습니다(5-1절 "한계"). 실수 오차가 생기는 원리는 5-3절에 정리했습니다.
- 제대로 고치려면 데이터 쪽에서 두 필터의 가중치 합이 같아지지 않도록 다시 설계해야 합니다. 예를 들어 size_13 X 필터의 가운데 값 7.5를 일반 값(0.3)으로 바꾸는 식입니다. 또는 동점일 때의 우선순위 규칙(tie-break)을 명세에 따로 정해야 합니다.
- `samples/data_error_cases.json` 실행(3-5절)에서 보듯, 스키마/크기/라벨 오류가 생기면 각각 `데이터/스키마`, `라벨 정규화`, `판정 불일치`, `수치 비교(동점)`로 분류됩니다. 그래서 data.json의 실패 3건이 "스키마나 라벨 문제가 아니라는 것"도 프로그램 출력만으로 확인할 수 있습니다.

### 4-3. 시간 복잡도 분석

**이론**: `mac()`은 N×N 행렬의 모든 칸을 정확히 한 번씩 방문하며 곱셈 1번과 덧셈 1번을 합니다. 그래서 연산 횟수는 **N²** 이고, 시간 복잡도는 **O(N²)** 입니다. 여기서 N은 한 변의 길이입니다. 칸 수(픽셀 수) P = N²으로 보면 O(P), 즉 데이터 크기에 선형입니다. 한 패턴을 판정하려면 필터 2개와 MAC을 해야 하므로 2N²번이지만, 상수배라 복잡도는 같습니다.

**측정 (모드 2, MAC 1회 평균 / 10회)**

```text
크기         평균 시간(ms)   연산 횟수(N²)     MAC 1회당(ns)
------------------------------------------------------------
3×3                 0.0006               9              66.7
5×5                 0.0011              25              43.6
13×13               0.0074             169              44.0
25×25               0.0183             625              29.2
```

- 연산 횟수는 9 → 625로 **약 69배** 늘었고, 측정 시간도 크기를 따라 단조 증가합니다.
- 다만 작은 N에서는 시간 증가율이 N²보다 작습니다. 그 이유는 MAC 1회당 시간이 3×3에서 약 60~70 ns로 가장 크고, 커질수록 25×25의 약 27~30 ns로 줄어들기 때문입니다. 3×3은 연산이 9번뿐이라서 함수 호출, `range` 생성, 행 참조 같은 **고정 비용**과 `perf_counter` 해상도가 측정값의 상당 부분을 차지합니다. 즉 실제 시간은 `t(N) ≈ a + b·N²` 꼴이고, N이 클수록 b·N² 항이 지배합니다.

**보조 측정 (더 큰 N에서 N² 비례 확인)** — `main.py`의 `mac()`/`benchmark_mac()`을 그대로 불러 25×25 ~ 400×400을 측정했습니다. (`docs/run_scaling_check.txt`)

```text
N×N        N²     평균(ms, 10회)   MAC 1회당(ns)   이전 크기 대비 시간 배율 / N² 배율
25×25         625        0.0182         29.1      -
50×50        2500        0.0703         28.1      3.87x / 4x
100×100      10000        0.2616         26.2      3.72x / 4x
200×200      40000        1.0468         26.2      4.00x / 4x
400×400     160000        4.4919         28.1      4.29x / 4x
```

- N을 2배로 늘리면 N²은 4배가 되고, 측정 시간도 **3.7 ~ 4.3배**로 거의 정확히 4배씩 늘었습니다.
- MAC 1회당 시간은 N과 상관없이 약 26 ~ 29 ns로 일정합니다. 이는 전체 시간이 연산 횟수 N²에 정비례한다는 직접적인 근거이며, **O(N²)** 임을 실험으로 확인한 것입니다.
- 같은 방식으로 1000×1000을 직접 재 보면 MAC 1회에 약 35 ms가 걸립니다(6-2절). 필터가 1,000개면 패턴 하나에 35초가 걸리는 셈입니다. CPU처럼 MAC을 하나씩 직렬로 처리하면 이렇게 느려지기 때문에, 수천 개의 MAC을 동시에 처리하는 NPU 같은 병렬 하드웨어가 필요합니다(6-3절).

### 4-4. 실패 0개가 되려면?
이번 data.json에서는 위의 이유로 실패가 3건 남습니다. 만약 필터 가중치가 동점을 만들지 않는 데이터였다면 실패 0건이 되었을 것이고, 그 이유는 다음 두 가지입니다.
1. **라벨 정규화**로 `'+'`/`'x'`/`'cross'`의 표기 차이에서 오는 거짓 FAIL을 없앴습니다.
2. **epsilon 비교**로 1e-16 수준의 반올림 오차가 판정을 뒤집는 일을 막았습니다.

`samples/data_error_cases.json`의 size_3_1, size_3_2가 그 예입니다. 표기가 `'+'`, `' X '`처럼 제각각이어도 PASS가 나옵니다.

## 5. 핵심 원리

### 5-1. MAC 점수가 높을수록 "더 비슷하다"고 볼 수 있는 이유
- **0과 1로 된 패턴과 필터**에서 곱 `p × f`는 두 칸이 **모두 1일 때만 1**이고, 나머지 경우는 0입니다. 그래서 MAC 점수는 곧 **패턴과 필터에서 동시에 칠해진 칸의 개수**, 즉 두 모양이 겹치는 정도입니다.
  - 미션 예시: 십자가 입력을 십자가 필터에 대면 5칸이 모두 겹쳐 5점입니다. X 필터에 대면 가운데 1칸만 겹쳐 1점입니다. 겹치는 칸이 많을수록 모양이 닮았다는 뜻이므로, 점수가 높은 필터의 모양으로 판정합니다.
- **필터 값이 실수**(가중치)이면, 가중치는 "그 칸이 판정에 얼마나 중요한가"를 뜻합니다. 점수는 겹친 칸들의 가중치 합이 됩니다. 중요한 칸에서 많이 겹칠수록 점수가 높아집니다.
- 수학적으로 MAC은 두 행렬을 길이 N²의 벡터로 펼친 **내적(dot product)** 입니다. 내적은 `a·b = |a||b|cos θ`이므로 두 벡터의 방향이 비슷할수록(θ가 작을수록) 커집니다. CNN의 합성곱 층도 이미지 위를 필터로 훑으며 같은 계산을 합니다. 그 값이 "이 위치에 이 모양이 있는가"에 대한 반응의 세기입니다.
- **한계**: MAC 점수는 크기를 맞추지 않은(정규화하지 않은) 값이라서, 모양이 얼마나 일치하는지뿐 아니라 **필터 가중치의 크기**에도 영향을 받습니다. 이번 data.json의 실패 3건이 바로 이 경우입니다. 예를 들어 size_13 X 필터는 가운데 한 칸에만 7.5라는 큰 가중치가 있습니다. 그래서 X 모양과 상관없이 가운데가 칠해진 십자가 입력도 7.5점을 받아, 십자가 필터 점수(0.3 × 25칸 = 7.5)와 동점이 됩니다. 모양 자체를 공정하게 비교하려면 두 벡터의 크기로 나누는 **코사인 유사도**를 쓰거나, 필터끼리 가중치 총합을 맞춰 설계해야 합니다.

### 5-2. 연산 횟수 N²과 O(N²)
- N×N 패턴의 칸은 N²개이고, MAC은 칸마다 곱셈 1번과 덧셈 1번을 합니다. 그래서 크기가 N일 때 연산 횟수는 정확히 N²이고, 시간은 `(MAC 1회 시간) × N²`에 비례합니다.
- 실측에서 N을 2배로 늘릴 때마다 시간이 약 4배씩 늘었고, MAC 1회당 시간은 크기와 상관없이 약 26 ~ 29 ns로 일정했습니다. 그래서 측정 결과가 O(N²) 경향을 보입니다. 측정 표와 작은 N에서의 예외(고정 비용)는 4-3절에 있습니다.

### 5-3. 부동소수점 오차가 생기는 이유와 epsilon이 필요한 이유
- 파이썬 `float`는 IEEE 754 배정밀도(64비트) 수입니다. 실제 값은 **2진수 유효숫자 53자리**까지만 저장됩니다.
- `0.1 = 1/10`은 2진수로 `0.000110011001100…`처럼 **끝없이 반복**되므로, 53자리에서 잘라 반올림해 저장합니다. 그래서 실제로 저장되는 값은 `0.1000000000000000055511151231257827…`이고, 0.1보다 아주 조금 큽니다. 0.3, 0.9, 4.9도 마찬가지로 정확히 나타낼 수 없습니다.
- **덧셈을 할 때마다** 결과를 다시 53자리로 반올림하므로 오차가 쌓입니다. `0.1 + 0.2`가 `0.30000000000000004`가 되는 이유이고, 이번 데이터에서 0.1을 9번 누적한 값이 `0.8999999999999999`가 된 이유입니다.
- 실수 덧셈은 결합법칙도 정확히 성립하지 않습니다. 그래서 수학적으로 같은 값이라도 **계산 경로가 다르면** 마지막 자리가 달라집니다. 예를 들어 "0.1을 9번 더한 값"과 "처음부터 저장된 0.9"는 다릅니다. MAC은 칸마다 덧셈을 하므로 이런 차이가 생기기 쉽습니다.
- 그래서 `==`로는 "수학적으로 같다"를 판단할 수 없습니다. `>`로 비교하면 반올림 오차가 어느 쪽으로 났는지에 따라 승자가 사실상 무작위로 정해집니다(4-2절에서 epsilon 없이 비교하면 셋 다 정답과 반대로 판정된 것처럼). **epsilon은 "이 정도 차이는 계산 오차로 보고 같은 값으로 취급한다"는 기준**입니다. 이 기준이 있어야 판정이 반올림 오차가 아니라 실제 점수 차이로 결정됩니다.
- epsilon 값은 데이터 규모에 맞춰야 합니다. 1e-9는 이번 데이터(25×25 이하, 오차 1e-15 수준)에는 충분하지만, 1000×1000처럼 덧셈이 백만 번이면 오차가 1e-6까지 커져 맞지 않습니다(6-2절).

## 6. 확장과 한계

### 6-1. 새 라벨(예: `'o'`)이 추가된다면 — 확장 순서
지금 코드에서 "라벨이 Cross와 X 두 개"라는 전제가 들어 있는 곳은 다음과 같습니다.
- `LABEL_ALIASES` (정규화 표)
- `parse_filter_entry()` (필터에 Cross와 X가 모두 있어야 함)
- `judge()` (점수 두 개를 비교)
- `evaluate_case()` (MAC 2회)
- `print_case()` (점수 두 줄 출력)

이 부분을 **바깥(입력 규칙)에서 안(판정)으로** 다음 순서로 고칩니다.

1. **데이터 규칙 정하기** — `'o'`가 무엇인지(예: 원 모양, 표준 라벨 `O`) 정합니다. expected와 필터 키에 어떤 표기로 오는지, 모든 크기에 `o` 필터가 있는지도 정합니다. 스키마가 정해져야 나머지를 결정할 수 있습니다.
2. **정규화** — `LABEL_O = "O"`를 만들고 `LABEL_ALIASES`에 `'o': O`(필요하면 `'circle'` 같은 별칭도)를 추가합니다. 라벨 목록 상수 `LABELS = (Cross, X, O)`를 하나 두고, 다른 코드는 모두 이 목록을 참조하게 바꿉니다. 이 단계까지만 해도 `'o'` 케이스는 `[라벨 정규화]` FAIL에서 벗어나 판정 단계로 넘어갑니다. 내부 로직은 표준 라벨만 알기 때문에, 입구에서 먼저 바뀌어야 뒤 단계가 의미를 가집니다.
3. **필터 로드** — `parse_filter_entry()`의 "필수 라벨" 검사를 `LABELS` 기준으로 바꿉니다. 예전 2-라벨 데이터와 호환해야 한다면 "필터에 있는 라벨만 후보로 쓴다"는 규칙으로 정합니다.
4. **판정** — `judge()`를 라벨 개수와 상관없이 동작하도록 일반화합니다. 라벨별 점수 `{label: score}`를 모두 계산하고, 최고 점수인 라벨을 찾습니다. 그 최고 점수와 **epsilon 이내인 다른 라벨이 하나라도 있으면** `UNDECIDED`입니다. 라벨이 두 개일 때는 지금과 똑같이 동작하므로 기존 결과가 그대로 유지됩니다.
5. **출력** — `print_case()`가 점수 딕셔너리를 돌며 라벨별 점수를 한 줄씩 출력하게 합니다. 성능 표는 MAC 1회 기준이라 그대로 둡니다. 다만 판정 1건에 드는 연산은 `라벨 수 × N²`으로 늘어난다는 점을 README에 적습니다.
6. **테스트** — 다음을 확인합니다.
   - (a) 기존 data.json의 결과(3 PASS / 3 FAIL)가 그대로인지 (회귀 확인)
   - (b) `'o'` 정답 케이스가 PASS인지
   - (c) `o` 필터가 빠진 크기는 `[데이터/스키마]` FAIL인지
   - (d) 세 점수 중 상위 두 개가 동점이면 `UNDECIDED`인지
   - (e) `'O'`, `' o '` 같은 표기도 정규화되는지

   이 항목들을 `samples/` 아래 JSON으로 추가해 매번 같은 결과가 나오는지 봅니다.

각 단계가 끝날 때마다 프로그램은 계속 실행되는 상태로 남습니다. 그래서 단계별로 실행해 보며 확인할 수 있습니다.

### 6-2. 1000×1000 패턴을 처리한다면
이 PC에서 `main.py`의 함수로 직접 측정한 값입니다.

| 항목 | 25×25 | 1000×1000 |
|---|---|---|
| 연산 횟수 N² | 625 | 1,000,000 (1,600배) |
| MAC 1회 시간 | 약 0.018 ms | 약 35 ms |
| JSON 텍스트 크기 (행렬 1개) | 수 KB | 약 14 MB |
| `json.loads` (행렬 1개) | 무시할 수준 | 약 0.66 초 |
| `Matrix.from_rows` 검증·생성 | 무시할 수준 | 약 0.77 초 |
| 메모리 (행렬 1개) | 수십 KB | 약 41 MB (순수 double 배열 8 MB의 약 5배) |
| 0.1을 백만 번 누적한 오차 | — | 약 1.3e-6 (**epsilon 1e-9보다 1,000배 큼**) |

**문제점**
- **시간**: MAC 한 번에 35 ms이므로 판정 1건(필터 2개)에 70 ms, 성능 측정(10회)에 0.35초가 걸립니다. 그런데 더 큰 병목은 MAC이 아니라 **로딩**입니다. JSON 파싱과 검증에 약 1.4초가 걸려서 MAC보다 40배 느립니다. `from_rows()`가 원소마다 `set()`을 호출하므로, 메서드 호출과 범위 검사가 백만 번 일어나기 때문입니다.
- **메모리**: 파이썬 `float`는 원소마다 독립된 객체(24바이트)이고, 리스트는 그 객체를 가리키는 포인터(8바이트)를 따로 들고 있습니다. 그래서 숫자 하나에 30바이트 넘게 듭니다. 필터 2개와 패턴 여러 개를 올리면 수백 MB가 됩니다. `json.load`도 파일 전체를 한 번에 메모리에 올립니다.
- **정확도**: 덧셈을 백만 번 누적하면 오차가 약 1e-6까지 커집니다. 그러면 고정 epsilon 1e-9로는 진짜 동점을 동점으로 잡지 못하고, 다시 반올림 오차가 판정을 정하게 됩니다.

**최적화 우선순위**
1. **먼저 측정하기** — 위 표처럼 실제로 재 보면, 추측과 달리 병목이 MAC이 아니라 로딩이라는 것을 알 수 있습니다. 가장 큰 비용부터 손댑니다.
2. **로딩 경로 줄이기** — `from_rows()`에서 원소마다 `set()`을 부르지 말고, 행 단위로 검증한 리스트를 그대로 보관합니다. 원소마다 생기는 함수 호출 비용을 없애는 것이 효과가 가장 큽니다.
3. **1차원 연속 배열** — `array('d')`처럼 길이 N²의 1차원 배열에 담으면 원소당 8바이트라서 메모리가 약 1/5로 줄어듭니다. `i * N + j` 한 번으로 위치를 찾으니 접근도 단순해집니다(보너스 과제 1의 방향).
4. **희소성 활용** — 이번 필터들은 대부분 0입니다. 십자가와 X 모두 0이 아닌 칸은 2N−1개뿐입니다. 0이 아닌 칸의 `(위치, 가중치)` 목록을 미리 만들어 두면, 1000×1000에서 곱셈이 백만 번에서 약 2천 번으로 줄어 O(N²)이 사실상 O(N)이 됩니다.
5. **정확도 보정** — 합산은 `math.fsum()`(오차 없는 합)이나 Kahan 합산으로 오차 누적을 줄입니다. 비교는 점수 크기에 비례하는 **상대 허용오차** `abs(a-b) <= max(rel_tol * max(|a|, |b|), abs_tol)`(`math.isclose`와 같은 방식)로 바꿉니다.
6. 그 이상은 표준 라이브러리 밖의 방법입니다. NumPy 벡터화(C 반복문과 SIMD), 행을 나눠 여러 프로세스로 병렬 처리, GPU/NPU 같은 방법이 있지만, 이번 과제의 제약 때문에 쓰지 않았습니다.

### 6-3. CPU의 직렬 처리 vs NPU의 병렬 처리 — 병목은 어디에 생기는가
MAC 하나는 곱셈 1번과 덧셈 1번으로 아주 단순합니다. 문제는 **개수**입니다. 25×25 필터 하나에 625번, 1000×1000에 백만 번입니다. 실제 CNN은 이미지의 모든 위치 × 수천 개 필터만큼 해야 하므로 수십억 번이 됩니다.

**CPU(그리고 이 프로그램)에서의 병목**
1. **직렬 실행** — 이중 `for`문이 N²개의 MAC을 하나씩 차례대로 처리합니다. 그래서 전체 시간은 `N² × (MAC 1회 시간)`이고, 측정한 MAC 1회 시간(약 26 ~ 29 ns)이 일정했기 때문에 시간이 그대로 N²에 비례했습니다.
2. **누산기 의존성** — `total += …`은 앞 덧셈의 결과가 나와야 다음 덧셈을 할 수 있습니다. 연산 장치가 여러 개 있어도 이런 형태의 반복문은 동시에 실행할 수 없는 의존 사슬이 됩니다.
3. **명령 처리 오버헤드** — 실제 곱셈·덧셈은 하드웨어에서 1 ns 안팎이면 끝납니다. 그런데 파이썬은 원소 하나마다 바이트코드 해석, 인덱싱, 새 `float` 객체 생성을 합니다. 그래서 26 ns의 대부분이 "계산이 아닌 일"입니다.
4. **메모리 접근** — MAC 1회마다 패턴 값과 필터 값 두 개를 읽어야 합니다. 계산은 적은데 읽을 데이터가 많아서(연산 강도가 낮아서), 데이터가 캐시에 다 들어가지 않을 만큼 커지면 메모리에서 값을 가져오기를 기다리는 시간이 늘어납니다.

**NPU는 어떻게 푸는가**
- MAC 유닛 수천 개를 격자(시스톨릭 배열)로 배치해, **한 클럭에 수천 개의 곱셈을 동시에** 합니다. 시간이 대략 `N² ÷ (MAC 유닛 수)`로 줄어듭니다. 각 칸의 곱셈은 서로 독립적이라 나눠서 동시에 하기 쉽습니다. MAC이 병렬 처리에 잘 맞는 이유입니다.
- 누산기 의존성은 **부분합**으로 나눕니다. 여러 유닛이 각자 일부를 더한 뒤, 덧셈 트리로 log 단계 만에 합칩니다.
- 필터 가중치를 칩 안의 메모리(SRAM)에 붙박아 두고 입력 데이터만 흘려보냅니다(weight-stationary). 같은 필터를 여러 입력에 재사용하므로 바깥 메모리(DRAM) 접근이 줄어듭니다.
- INT8, FP16 같은 낮은 정밀도를 써서 유닛을 작게 만들어 더 많이 넣고, 옮길 데이터 크기도 줄입니다.

**정리**: CPU에서의 병목은 **연산을 하나씩 처리하는 직렬 구조**와 **명령 처리 오버헤드**입니다. NPU가 연산을 병렬로 처리하면, 병목은 **수천 개의 MAC 유닛에 데이터를 제때 공급하는 메모리 대역폭**으로 옮겨 갑니다. 그래서 NPU 설계에서는 연산기 개수만큼이나 데이터 재사용과 칩 안의 메모리가 중요합니다.
