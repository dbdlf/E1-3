# Mini NPU Simulator

AI 모델이 하는 핵심 계산인 **MAC(Multiply-Accumulate) 연산**을 직접 구현해서, 입력 패턴이 **십자가(Cross)** 와 **X** 중 어느 쪽에 가까운지 판별하는 Python 콘솔 프로그램입니다.
3×3 사용자 입력과 `data.json`(5×5, 13×13, 25×25)을 분석하고, 크기별 연산 시간을 측정해 시간 복잡도 O(N²)를 확인합니다.

- Python 3.8 이상, **표준 라이브러리만 사용** (`json`, `time`, `re`, `math`, `os`, `sys`, `unicodedata`)
- NumPy 등 외부 라이브러리는 쓰지 않았고, MAC 연산은 이중 반복문으로 직접 구현했습니다.

## 1. 실행 방법

```bash
python main.py
```

실행하면 모드를 고릅니다.

| 입력 | 모드 | 설명 |
|---|---|---|
| `1` | 사용자 입력 (3x3) | 필터 A, B와 패턴을 한 줄씩(공백 구분) 입력 → MAC 점수 / 판정 / 3×3 성능 출력 |
| `2` | data.json 분석 | `data.json`의 필터·패턴을 일괄 판정 → PASS/FAIL, 크기별 성능 표, 결과 요약 출력 |

- **data.json 위치**: `main.py`와 같은 폴더의 `data.json`을 기본으로 읽습니다. 현재 작업 폴더가 달라도 동작합니다.
- 다른 JSON 파일을 분석하려면 경로를 인자로 넘깁니다.

```bash
python main.py samples/data_error_cases.json
```

- 입력을 파이프로 넣을 수도 있습니다. 이때는 입력값도 화면에 그대로 찍혀서 실행 기록을 읽기 쉽습니다.

```bash
echo 2 | python main.py
```

## 2. 구현 요약

### 2-1. 데이터 구조 — `Matrix`
- n×n 2차원 리스트를 감싼 클래스입니다. `get(row, col)` / `set(row, col, value)`로 특정 위치의 값을 읽고 씁니다. 범위를 벗어나면 `IndexError`가 납니다.
- `Matrix.from_rows(rows)`는 JSON 배열을 검증해서 행렬로 바꿉니다.
  - 배열인지, 정사각형인지(각 행의 열 수 = 행 수), 모든 값이 유한한 숫자인지 확인합니다. `bool`, 문자열, `NaN`, `inf`는 거부합니다.
- 크기에 제한이 없어서 3×3, 5×5, 13×13, 25×25는 물론 400×400도 처리합니다. (아래 보조 측정 참고)

### 2-2. 라벨 정규화
프로그램 내부에서는 **표준 라벨 `Cross`, `X` 두 개만** 사용합니다. 바깥 데이터의 표기는 모두 `normalize_label()` 한 곳에서 변환합니다.

| 원본 표기 (앞뒤 공백 제거, 대소문자 무시) | 표준 라벨 |
|---|---|
| expected `'+'`, filter 키 `'cross'` | `Cross` |
| expected `'x'`, filter 키 `'x'` | `X` |
| 그 밖의 값 (예: `'o'`) | 정규화 실패 → 해당 케이스 FAIL `[라벨 정규화]` |

**정규화를 하는 이유**: `data.json`은 같은 뜻을 서로 다른 기호로 씁니다. 정답(expected)은 `'+'`/`'x'`, 필터 키는 `'cross'`/`'x'`입니다. 이 문자열을 그대로 비교하면 판정 결과 `"cross"`와 정답 `"+"`는 영원히 다르다고 나와서, 로직이 맞아도 FAIL이 됩니다. 입력 지점에서 표준 라벨로 한 번 통일해 두면, 출력과 PASS/FAIL 비교가 모두 같은 기준(`Cross`/`X`)으로 이루어집니다.

### 2-3. MAC 연산 — `mac(pattern, filt)`
```python
total = 0.0
for i in range(n):
    for j in range(n):
        total += pattern[i][j] * filter[i][j]   # 곱하고(Multiply) 누적(Accumulate)
```
- 두 행렬의 크기가 다르면 `ValidationError`를 던집니다. 모드 2에서는 이를 미리 검사해 케이스 단위 FAIL로 처리합니다.
- 결과는 `float` 점수입니다.

### 2-4. 점수 비교 정책 (epsilon)
- `abs(score_a - score_b) < 1e-9` 이면 **동점 → `UNDECIDED`(모드 1에서는 "판정 불가")** 로 봅니다.
- 동점이 아니면 점수가 큰 쪽의 라벨로 판정합니다. 모드 1은 `A`/`B`, 모드 2는 `Cross`/`X`입니다.
- `UNDECIDED`는 expected(Cross/X)와 같을 수 없으므로 항상 FAIL입니다.
- 진단을 돕기 위해 동점 FAIL 사유에 **"epsilon 없이 `>`로만 비교했다면 어떻게 판정됐을지"** 도 함께 출력합니다.

### 2-5. 입력 검증과 오류 처리
| 상황 | 처리 |
|---|---|
| 모드 선택에 1, 2 외의 값 | 안내 후 다시 입력 |
| 모드 1: 한 줄의 숫자 개수가 3이 아님 (열 수 불일치) | `입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요.` → **그 줄만** 다시 입력 |
| 모드 1: 빈 줄 (행 수 부족) | 행 수 부족 안내 → 그 줄 다시 입력 |
| 모드 1: 숫자로 바꿀 수 없는 값, `inf`/`nan` | 숫자 파싱 오류 안내 → 그 줄 다시 입력 |
| 모드 2: 파일 없음 / JSON 문법 오류 | 오류 메시지 출력, 케이스 0개로 요약까지 정상 진행 |
| 모드 2: 필터가 정사각형이 아님, 키의 N과 크기가 다름, cross/x 누락 | 그 크기 필터만 로드 실패. 그 크기를 쓰는 패턴은 FAIL `[데이터/스키마]` |
| 모드 2: 패턴 키가 `size_{N}_{idx}` 형식이 아님 | FAIL `[데이터/스키마]` |
| 모드 2: 키의 N에 해당하는 필터 없음 | FAIL `[데이터/스키마]` |
| 모드 2: **패턴과 필터의 크기 불일치** | FAIL `[데이터/스키마]` `크기 불일치: 패턴 4×4 ≠ size_3 필터 3×3` |
| 모드 2: input/expected 누락, 숫자가 아닌 값 | FAIL `[데이터/스키마]` |
| 모드 2: 예상 못 한 예외 | 해당 케이스만 FAIL로 격리하고 다음 케이스 계속 |
| 입력 스트림 종료(EOF), Ctrl+C | 안내 문구 후 정상 종료 (traceback 없음) |

FAIL 사유는 `데이터/스키마`, `라벨 정규화`, `수치 비교(동점)`, `판정 불일치` 네 가지로 분류해 출력합니다. 그래서 실패가 나면 **데이터 문제인지, 로직 문제인지, 수치 비교 문제인지** 바로 구분할 수 있습니다.

### 2-6. 성능 측정
- `time.perf_counter()`로 **MAC 함수 호출 구간만** 잽니다. 입력·출력·파일 읽기 시간은 포함하지 않습니다.
- 워밍업 1회는 측정에서 빼고, **10회 반복 측정한 평균(ms)** 을 출력합니다.
- 표에는 `크기(N×N) / 평균 시간(ms) / 연산 횟수(N²)`를 싣고, 복잡도 분석을 돕기 위해 `MAC 1회당(ns)` = 평균 시간 ÷ N² 도 함께 보여 줍니다.
- 모드 1은 3×3을 측정합니다. 모드 2는 3×3(미션 소개의 십자가 필터와 X 패턴)과 data.json의 5×5, 13×13, 25×25를 측정합니다.

### 4-2. 실패 원인 분석

실패 3건을 **데이터/스키마 문제 → 로직 문제 → 수치 비교 문제** 순서로 하나씩 점검했습니다.

**① 데이터/스키마·라벨 문제인가? → 아니다.**
세 필터(size_5, 13, 25)는 모두 정사각형이고, 키의 N과 크기가 같고, cross/x가 모두 있어서 정상 로드되었습니다. 6개 패턴도 키 형식(`size_{N}_{idx}`), 크기(패턴 N×N = 필터 N×N), 숫자 값 검증을 모두 통과했습니다. expected `'x'`, `'+'`도 각각 `X`, `Cross`로 정상 정규화되었습니다. 그래서 FAIL 분류에 `데이터/스키마`나 `라벨 정규화`는 0건입니다.

**② MAC 로직 문제인가? → 아니다.**
점수를 손으로 계산한 값과 비교했습니다.
- size_5_2: 십자가 입력 9칸 중 가운데 1칸은 0.9, 나머지 8칸은 1.0 → 8 × 1.0 + 0.9 = **8.9** ✔
- size_25_2: 십자가 입력 49칸 → 48 × 1.0 + 4.9 = **52.9** ✔
- size_13_1: X 입력 25칸 → 24 × 0.3 + 7.5 = **14.7** ✔

출력값과 모두 일치하고, 나머지 3건도 정상적으로 PASS입니다. 로직(곱셈, 누적, 큰 쪽 선택)에는 문제가 없습니다.

**③ 수치 비교(동점) 문제다 — 근본 원인은 필터 가중치 설계.**
실패한 세 케이스는 **수학적으로 두 점수가 정확히 같도록** 필터 가중치가 정해져 있습니다.

| 케이스 | Cross 필터 쪽 계산 | X 필터 쪽 계산 | 실수 계산 결과 |
|---|---|---|---|
| size_5_1 (X 입력) | 가운데 0.9 × 1 = 0.9 | 대각선 9칸 × 0.1 = 0.9 | 0.9 vs 0.8999999999999999 |
| size_13_2 (십자가 입력) | 십자가 25칸 × 0.3 = 7.5 | 가운데 7.5 × 1 = 7.5 | 7.499999999999997 vs 7.5 |
| size_25_1 (X 입력) | 가운데 4.9 × 1 = 4.9 | 대각선 49칸 × 0.1 = 4.9 | 4.9 vs 4.899999999999999 |

- 0.1, 0.3은 2진수 부동소수점으로 정확히 나타낼 수 없습니다. 그래서 여러 번 더하면 마지막 자리에 1e-16 ~ 1e-15 수준의 오차가 쌓입니다. 이 때문에 "같아야 할" 두 점수가 아주 조금 다르게 나옵니다.
- 이 차이(최대 2.66e-15)는 허용오차 1e-9보다 백만 배 이상 작습니다. 따라서 epsilon 정책에 따라 **동점(UNDECIDED)** 이 되고, expected와 다르므로 FAIL입니다.
- **epsilon 없이 `>`로만 비교했다면** 판정은 반올림 오차의 방향에 따라 정해졌을 것입니다. 실제로 size_5_1 → Cross, size_13_2 → X, size_25_1 → Cross로 **셋 다 정답과 반대**가 나옵니다. 즉 epsilon이 없어도 결과는 여전히 FAIL입니다. 다만 이 경우 "판정 불일치"로 보여서 **로직 버그처럼 오진하게** 됩니다. epsilon 정책 덕분에 진짜 원인(필터가 이 입력을 구별하지 못함)이 `수치 비교(동점)`로 정확히 드러납니다.

**결론 및 개선 방향**
- 3건 모두 `수치 비교(동점)` 분류이며, 근본 원인은 **data.json 필터 가중치 설계(데이터 문제)** 입니다. 프로그램 로직의 결함은 아닙니다.
- PASS 수를 늘리려고 data.json이나 expected를 고치거나 epsilon을 0으로 낮추지 **않았습니다**. 그렇게 하면 문제를 숨기는 것이고, 반올림 오차에 판정을 맡기게 되기 때문입니다.
- 제대로 고치려면 데이터 쪽에서 두 필터의 가중치 합이 같아지지 않도록 다시 설계해야 합니다. 예를 들어 size_13 X 필터의 가운데 값 7.5를 일반 값(0.3)으로 바꾸는 식입니다. 또는 동점일 때의 우선순위 규칙(tie-break)을 명세에 따로 정해야 합니다.
- `samples/data_error_cases.json` 실행(3-5절)에서 보듯, 스키마/크기/라벨 오류가 생기면 각각 `데이터/스키마`, `라벨 정규화`, `판정 불일치`, `수치 비교(동점)`로 분류됩니다. 그래서 data.json의 실패 3건이 "스키마나 라벨 문제가 아니라는 것"도 프로그램 출력만으로 확인할 수 있습니다.

### 4-3. 시간 복잡도 분석

**이론**: `mac()`은 N×N 행렬의 모든 칸을 정확히 한 번씩 방문하며 곱셈 1번과 덧셈 1번을 합니다. 그래서 연산 횟수는 **N²** 이고, 시간 복잡도는 **O(N²)** 입니다. 여기서 N은 한 변의 길이입니다. 칸 수(픽셀 수) P = N²으로 보면 O(P), 즉 데이터 크기에 선형입니다. 한 패턴을 판정하려면 필터 2개와 MAC을 해야 하므로 2N²번이지만, 상수배라 복잡도는 같습니다.

**측정 (모드 2, MAC 1회 평균 / 10회)**

```text
크기         평균 시간(ms)   연산 횟수(N²)     MAC 1회당(ns)
------------------------------------------------------------
3×3                 0.0006               9              66.7
5×5                 0.0011              25              43.6
13×13               0.0074             169              44.0
25×25               0.0183             625              29.2
```

- 연산 횟수는 9 → 625로 **약 69배** 늘었고, 측정 시간도 크기를 따라 단조 증가합니다.
- 다만 작은 N에서는 시간 증가율이 N²보다 작습니다. 그 이유는 MAC 1회당 시간이 3×3에서 약 60~70 ns로 가장 크고, 커질수록 25×25의 약 27~30 ns로 줄어들기 때문입니다. 3×3은 연산이 9번뿐이라서 함수 호출, `range` 생성, 행 참조 같은 **고정 비용**과 `perf_counter` 해상도가 측정값의 상당 부분을 차지합니다. 즉 실제 시간은 `t(N) ≈ a + b·N²` 꼴이고, N이 클수록 b·N² 항이 지배합니다.

**보조 측정 (더 큰 N에서 N² 비례 확인)** — `main.py`의 `mac()`/`benchmark_mac()`을 그대로 불러 25×25 ~ 400×400을 측정했습니다. (`docs/run_scaling_check.txt`)

```text
N×N        N²     평균(ms, 10회)   MAC 1회당(ns)   이전 크기 대비 시간 배율 / N² 배율
25×25         625        0.0182         29.1      -
50×50        2500        0.0703         28.1      3.87x / 4x
100×100      10000        0.2616         26.2      3.72x / 4x
200×200      40000        1.0468         26.2      4.00x / 4x
400×400     160000        4.4919         28.1      4.29x / 4x
```

- N을 2배로 늘리면 N²은 4배가 되고, 측정 시간도 **3.7 ~ 4.3배**로 거의 정확히 4배씩 늘었습니다.
- MAC 1회당 시간은 N과 상관없이 약 26 ~ 29 ns로 일정합니다. 이는 전체 시간이 연산 횟수 N²에 정비례한다는 직접적인 근거이며, **O(N²)** 임을 실험으로 확인한 것입니다.
- 이 결과대로라면 1000×1000 필터 하나에 약 2.7천만 ns(≈ 27 ms)가 걸리고, 필터가 수천 개면 수십 초가 걸립니다. CPU처럼 MAC을 하나씩 직렬로 처리하면 이렇게 느려지기 때문에, 수천 개의 MAC을 동시에 처리하는 NPU 같은 병렬 하드웨어가 필요합니다.

### 4-4. 실패 0개가 되려면?
이번 data.json에서는 위의 이유로 실패가 3건 남습니다. 만약 필터 가중치가 동점을 만들지 않는 데이터였다면 실패 0건이 되었을 것이고, 그 이유는 다음 두 가지입니다.
1. **라벨 정규화**로 `'+'`/`'x'`/`'cross'`의 표기 차이에서 오는 거짓 FAIL을 없앴습니다.
2. **epsilon 비교**로 1e-16 수준의 반올림 오차가 판정을 뒤집는 일을 막았습니다.

`samples/data_error_cases.json`의 size_3_1, size_3_2가 그 예입니다. 표기가 `'+'`, `' X '`처럼 제각각이어도 PASS가 나옵니다.
